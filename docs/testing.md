# Writing and timing tests

Read before writing, editing, merging, deleting, or timing a test. `bin/test` usage is in the root `AGENTS.md` and in the comment at the top of the script.

## Choosing a fixture

- Use the test helpers in `crates/liboxen/src/test.rs` (`run_empty_local_repo_test` and the like) for unit tests in the lib code.
- Choose the lightest helper that meets the test's actual needs. Rough cost order, cheapest first: `run_empty_dir_test_async`, `run_empty_local_repo_test_async`, `run_one_commit_local_repo_test_async`, `run_readme_remote_repo_test` (remote with a single README pushed), `run_one_commit_sync_repo_test` (local and remote, one inline commit), `run_training_data_repo_test_no_commits_async` (training files written, not committed), `run_training_data_repo_test_fully_committed_async` (training files and one commit, no remote), `run_training_data_fully_sync_remote` (training files, 6 commits, a remote, and a push, about 1 to 2 s per test). Reach for the training-data helpers **only** when the assertions depend on the specific tree structure (paths under `nlp/classification/`, `annotations/test/`, and so on). A test that only modifies, renames, or asserts about `README.md` belongs on `run_readme_remote_repo_test`, not `run_training_data_fully_sync_remote`. A test whose only training-tree file is `annotations/train/bounding_box.csv` belongs on `run_bounding_box_csv_repo_test_fully_committed_async` (local, one commit) or `run_remote_repo_test_bounding_box_csv_pushed` (pushed to a remote), which write that file with the same rows the training tree does.
- A helper that hands a test back a `(LocalRepository, RemoteRepository)` pair has already attached that repo to that remote, so a test needing two actors takes that repo as one of them and clones only the other. Opening with `|_, remote_repo|` and then cloning twice builds a repo the helper already built. Which role it plays depends on the scenario: it is the user who advances the remote when the test is about a clone that has fallen behind, and the user who pushes first when the test is about the second clone hitting a conflict.
- Only copy real fixture images into a test repo (`test::test_img_file_with_name` and `util::fs::copy`) when an assertion depends on image content or metadata (dimensions, mime type, resize behavior). When the test only needs files that exist, get added, get modified, or get counted, write small inline text files instead: `util::fs::write_to_path(dir.join(format!("cat_{i}.jpg")), format!("cat {i}"))`, or `test::populate_dir_with_txt_files`. Change a file's content with `test::modify_txt_file` rather than re-encoding an image through `util::image::resize_and_save`. `add`, `commit`, `status`, and `rm` never decode file content, so a `.jpg` holding text exercises the same code paths without the fixture IO or the image encode.
- When a test needs a small directory of placeholder text files, call `test::populate_dir_with_txt_files(dir, prefix, count)` instead of open-coding `util::fs::create_dir_all` and a loop over `write_txt_file_to_path`.
- Files under `data/test/` exist to serve specific tests. When you delete or rewrite a test, check whether any fixture file under `data/test/` is now unreferenced and delete the orphan in the same PR. Never add a fixture file speculatively or "for a future test". Add it only when the test that uses it already exists.
- When possible, put tests in the higher-level `repositories` module rather than the lower-level, version-specific implementation: `repositories/commits.rs` rather than `core/v_latest/commits.rs`.
- Tests create unique temporary directories and clean up automatically.

## One fixture, many assertions

- Add assertions to a test that already builds the right fixture rather than writing a new test, and go looking for that host before writing the test rather than after review finds it. A new test pays for its whole fixture again, priced by the list above. A test's name only has to name something important the test checks, not everything it checks, so a name that fits less well after the addition is not a reason to build a second fixture: put the rest in the assertion message, as in `assert_eq!(mergeability.conflicts.len(), 1, "both branches rewrote README.md")`. Write a separate test only when carrying the assertion would need a tear-down and re-setup partway through the host, when the host's fixture data decides the expected value (asserting against a value computed from the fixture usually dissolves that), or when the host becomes hard to follow.
- Two tests in one file that open the same helper and reach the same state before their first assertion are one test, and so are two whose scenarios are prefixes of one another: assert at the earlier state, then keep building to the later one and assert again. The prefix case holds across files too. A test in one module that stops partway through a scenario another module's test runs to completion (a subtree clone and commit that a push test also clones, commits, and then pushes) is already covered, so search the other modules' tests for the scenario before writing it.
- Tests that open the same remote helper and then each clone it their own way (a subtree, a depth, `--all`, a branch) are one test as well, since a clone only reads the remote. Clone into a separate directory per case under the one fixture, and do any step that changes the remote, such as pushing a new branch, after the clones that expect it unchanged.
- Tests that build the same fixture and then each edit it their own way are one test when each case can work in its own corner of it. Give each case its own workspace under the one fixture, and its own branch when it commits, as the `repositories::workspaces::data_frames` tests do. A case that diffs two commits gets its own directory in a shared first commit and a commit of its own on top of the previous case's, so diffing its commit against the one before it shows only its changes, as the `api::client::diff` test does. Only a step that leaves the fixture unusable for the cases after it, such as deleting a commit's node, has to come last.
- A change that edits a test also checks the other tests in that module that open the same fixture helper, and merges the ones the rules above make one test. Make a small merge in the same change, and open an issue for a larger one. The rules above otherwise fire only when a new test is written, so tests that already share a fixture stay separate until a change sets out to merge them.
- Bound a verification loop to the cases that separate a pass from a failure, since every iteration is a full execution of the code under test. A sweep over every ordered pair drawn from N commits, or one call repeated 200 times to check that the answer never varies, looks thorough while costing more than the rest of its module. Ask what the loop recomputes before writing it: a reference value derived from N distinct inputs belongs outside the loop, walked once and shared across the cases, which keeps every case and every assertion. A repeated call that samples for nondeterminism the code can no longer produce covers nothing that one call does not.

## Merging or deleting tests keeps their coverage

A change that merges or deletes tests keeps executing every line of non-test code the old tests executed. Much of that never shows in an assertion (a server branch a fixture's setup happens to reach, an error path a misnamed test hits by accident), and reading the code cannot settle which lines a test reaches, so measure it.

1. In a fresh worktree of the base commit and one of the change, run `eval "$(cargo llvm-cov show-env --sh)"`, `cargo llvm-cov clean --workspace`, `bin/test`, and `cargo llvm-cov report --lcov --output-path <arm>.lcov`. That environment instruments the `oxen-server` that `bin/test` starts as well, which writes its counts when `bin/test` stops it.
2. Compare the non-test lines the two runs executed, matching lines by file and source text, since edits shift line numbers.
3. Each line only the base run reached either runs again (choose the merged test's paths, data, or loop entries so that it does, or add a call and an assertion to a test whose fixture already reaches it), or belongs to code the change deletes on purpose. A line reached only by tests the change left alone is run-to-run variation, so confirm each candidate by running just the touched modules under coverage on the base worktree.

## Timing tests

- `bin/test --timings` prints each test's duration next to its result, where plain `cargo test` reports only a per-binary total. Doctests are skipped.
- **Measure what a test costs with `--test-threads=1`.** A duration from a parallel run includes the time a test spent waiting on its neighbors, even when the filter selects a single module: the 49 `repositories::commits::` tests summed 12.7 s run together and 2.7 s run one at a time. A change that removes tests therefore makes the tests it left alone look faster in a parallel run.
- Decide whether merging tests pays from each test's own duration taken that way, never from a module total taken in a full run (a module reported at 29 s there sums to 1.6 s alone). Dozens of tests at a few hundredths of a second that each build the same fixture spend most of that time in the fixture, and a case moved into a merged test costs only its own operations, so the merge recovers most of their summed time: 42 such `repositories::workspaces::data_frames` tests summing to 1.4 s became 6 summing to 0.66 s.
- **Run both sides of a timing comparison from fresh `git worktree` checkouts, and alternate them.** A long-lived working tree reports the same unchanged tests markedly slower than a worktree of the same commit does (a 23-test set summed 14.8 s in one against 11.5 s in a worktree, with identical code), so a working-tree-against-worktree comparison charges that gap to whichever side the working tree is on. Run the arms in alternating order, since in a fixed order a drifting machine shows up as a change in whichever side always runs second. Discard the first run after a build (a cold run reads two to three times high), and keep both sides on the same base commit (`main` moves fast enough that an older base is a different suite).
- Sanity-check every result by summing the tests the change did not touch, which should match across arms to a percent or two, and distrust the comparison when they do not.

## Process state, timing, and sizes

- Under `cargo test` each test target compiles to its own test binary and runs as a separate process (the lib's unit tests are one binary, each file under `tests/` is another, and doctests are another), so process-global state (env vars, `OnceLock`, `LazyLock`, and `OnceCell` singletons, cached HTTP clients and connection pools, static caches keyed by name) is shared only among the tests within one binary, where it can leak from one test into the next. New tests must not depend on per-process state that isn't explicitly re-initialized:
  - don't `std::env::set_var` in a test body without a scoped restore (or a `Once`-guarded write of a constant)
  - don't cache anything at process scope keyed on values a sibling test might reuse (bucket, workspace, or repo names): use UUID-derived values
  - don't build a `LazyLock` whose init reads state a sibling test might have already read at a different value

  When a test needs exclusive access to a process-wide singleton (a DB-cache flush, a global counter), gate it with `#[serial_test::serial(named_key)]`, pairing every test that touches the same singleton on the same key. `serial_test`'s lock is process-local, so it serializes only tests within one binary, which is the only place the hazard exists. Canonical examples: the S3 `cloud_reads` tests mint UUID-tagged buckets in `setup()` so `polars-io`'s cloud-store cache can't collide, and the `df_db` flush tests share `#[serial_test::serial(df_db_cache)]`.
- Never sleep in a test. A commit records its time to below a second, so two commits made back to back already sort by date, and work that runs in the background gets polled at a 2 ms interval against a bounded deadline rather than waited out.
- Never test that an operation moves its work off the calling thread. Whether it hands blocking work to `spawn_blocking` shows in its code, and a test of that checks tokio rather than the operation.
- Test runs set `OXEN_STREAM_SEGMENT_SIZE` to 128 KiB through `bin/test`, so any file larger than about 128 KiB exercises the streamed-transfer and chunked-download paths. Size a test file for that path as `stream_segment_size() + N` with N small (1 byte to about 1 MiB), not a hardcoded multi-MB value. A 1.1 MiB test file exercises the same chunked-transfer code as a 100 MB production file.
- A test of the S3 version store's multipart upload lowers the store's `oneshot_size` and sizes its data from `MIN_PART_SIZE` (`MIN_PART_SIZE + 1` for a short last part, `2 * MIN_PART_SIZE` for an exact part boundary). Every upload at or under `oneshot_size`, 100 MiB by default, goes out as a single PUT, so a test that only makes its data large never reaches the multipart path.

## Doctests

Never add a ```` ```ignore ```` doctest. An `ignore` fence is neither compiled nor run, so the example rots silently while still looking maintained. Write it so it runs **without `oxen-server`**: `cargo test --doc` has to pass on its own, so an example may use the filesystem but must not need a running server or a reachable remote. `liboxen::test`'s helpers are available to doctests: `test::run_empty_dir_test` for a sync example, and `test::run_empty_dir_test_async` with a hidden `# #[tokio::main]` line for an async one. Both make a unique temp directory, and only the sync helper removes it afterward. When an example needs a server or a remote, use `no_run` with a line above it saying so, or don't write the example. A doctest on a private item can never run, since it compiles as an external crate.
